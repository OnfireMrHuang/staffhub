# 薪酬任务、结果复核与 HR 归档

日期：2026-10-16，更新于2026-10-17。本规格覆盖同日及此前规格中的员工独立规则分类、核算自动归档和薪酬核算页面布局。

## 规则

规则分类仅保留全局规则、直播间规则。员工规则合并至全局规则，取消员工筛选条件，全局规则适用全部有效主播。旧当前员工规则保留名称与计算配置、移除员工条件并生成新的全局草稿版本；历史发布任务及归档快照仍按原依据读取，新范围需要重新发布。

直播间规则集保持共享直播间、补贴/保费系数/时薪各至多一条的约束。各类型的既有计算方式不变。全局内同类规则仍按补贴累加、保费候选总额取最大、保底金额取最大及加成金额求和处理。月薪仍为 max(最终保底金额,累计加成金额)+总补贴。

## 核算任务与页面

系统在每月1日00:00（Asia/Shanghai）自动生成上个月的一条待核算任务。例如2026-11-01生成2026-10任务。月份唯一，规则发布不生成任务，也不要求选择月份。即使没有已发布规则或月度数据，任务仍应生成，等待 HR 准备与确认数据。调度器仅创建任务，不自动核算、归档或发布工资条。

一个月份显示一条月度核算任务，核算前展示当前已发布规则与员工月度数据的准备情况。列表仅包含筛选栏和只读任务摘要，可按月份、状态和文本检索；摘要包含任务月份、规则数量、人员数量与状态。点击摘要在当前页进入任务详情，返回时保留列表筛选。

详情显示返回、核算操作和基础信息（月份、状态、数据集版本、输入规则、员工范围、核算及归档时间）。核算/重新核算必须二次确认。核算后状态为待复核，不自动归档。旧式部门任务作为历史兼容输入，不与新版任务混算。

## 规则确定与任务生成

- HR 点击“核算”并二次确认时，读取最新已发布的完整规则版本及最新已确认月度汇总；此前发布到哪个月份不再是输入条件。员工名单、行键、数据版本、来源修订和月末判断基准在这次核算中确定。
- 保存草稿不改变可用发布版本；直播间规则集整体发布，共同版本和完整成员同时替换。修改直播间范围后，旧发布范围继续生效，须先发布更新或删除旧规则集，其他规则集才可发布占用这些直播间。发布不要求已有月度数据。
- 核算成功后原子保存规则、员工、来源数据、计算结果和版本快照。任何输入校验或计算失败均不写入部分结果，待核算任务继续保留。缺少规则或有效主播数据时不能核算。
- 核算后发布新版本、删除有效规则或更改来源/月度数据时，原结果保留并标记待重新核算；归档前必须重新核算和复核。仅编辑未发布草稿不会使原结果失效。归档后的所有依据及结果保持冻结。
- 调度以工资月份为幂等键；重复触发、进程重启或失败重试都不得生成重复任务。停机恢复后，从启用月份对应的应核算月起补齐已到期且缺失的月份，不生成未来任务。首次启用仅从当时应生成的上个月开始，不批量创建更早历史任务。
- 已存在的历史任务、已核算批次及归档月保留，不因调度重复创建或清空。旧部门/旧发布任务继续走历史兼容路径；新月度自动任务不提供逐条规则输入撤回操作。

## 两张结果表

详情以水平页签提供“月度核算明细”和“员工月薪汇总”，两张均为结果表并支持检索和导出。只有月度核算明细支持自定义追加表头和编辑，员工月薪汇总只读。

- 月度核算明细：员工×直播间×月份。固定关联标识与人员、直播间、期间信息只读以保持稳定行键；统计数值和核算结果可直接修改，包括计算所得字段。修改任一字段不会自动重算其他字段，也不会立即更新汇总表。
- 员工月薪汇总：只有明确执行“应用”后才更新。应用按员工ID汇总明细中当前“总计月薪”值，保持一名员工一行。其他数值和自定义字段不自动作为工资项相加。
- 追加表头：仅在该任务的明细表配置名称和类型（文本/数字/金额），名称不可为空或与固定字段/同表追加字段重名。追加字段用于补充数据，不自动参与计薪。
- 编辑立即保存为待应用草稿，要求填写理由，记录操作人、时间、前后值和版本；应用保留相应记录。人工编辑不回写运营表，不覆盖原始核算依据。
- 编辑或新增表头后显示“待应用”，汇总仍展示上次应用的结果；应用操作完成后才可提交 HR 归档。无效数值、未知字段、负数最终工资和过期版本均拒绝整次写入。

重新核算前提示其影响，避免静默丢弃已存在的人工修正。旧归档直接读取历史结果，不能迁移后重算历史金额。

## HR 手动归档

只有复核无误后，由具备“薪酬归档”权限的 HR 执行手动归档，需二次确认。管理员演示身份可执行归档。归档必须有完整计算结果，明细修改必须已经应用，并验证来源、确认月度数据和已发布规则没有在核算后发生变化。若已变化，要求刷新来源并重新核算，不能将旧结果误记为当前结果。

保留既有工资条发布流程：归档后，具备“工资发布”权限的人员可在任务详情确认发布工资条，员工才可在本人资料中查看。归档不会自动发布，已发布结果继续只读。

归档写入操作人、时间、复核版本及最终两表快照，再更新全局 archivedMonths。归档前来源仍可纠正；归档后原始数据、运营统计、任务结果及追加字段禁止变更或重算。原先已归档月份保持归档，不自动解锁。

## 存储设计（MySQL）

沿用规则版本与规则集表，发布版本不关联工资月份。`compensation_rule_versions` 保存不可变发布定义；当前规则/规则集指向最新可用发布版本。草稿与发布版本独立保存，整组发布以事务替换，旧版本继续可被核算记录引用。

| 表 | 主要字段与约束 |
| --- | --- |
| `payroll_monthly_jobs` | id、salary_month（月首DATE，UNIQUE）、scheduled_at、created_at、状态、当前核算版本、核算人/时间、归档人/时间、并发版本；生成时不绑定规则或数据版本 |
| `payroll_schedule_state` | 单例任务配置：时区Asia/Shanghai、启用对应工资月、最近完成检查时间；仅记录检查进度，不代替任务表的唯一约束 |
| `payroll_calculation_runs` | job_id、run_no（组合唯一）、触发HR、开始/结束时间、状态、数据集版本/来源修订、月末基准、错误信息；HR核算时创建 |
| `payroll_run_rule_snapshots` | run_id、rule_id（组合唯一）、发布版本ID、完整规则定义；直播间规则集另保存组ID、共同版本和完整成员ID |
| `payroll_run_input_snapshots` | run_id、来源数据版本、员工与直播间资料、参与员工名单、行键及原始统计快照；与结果同次提交 |

后台按上述时区执行月初定时任务，使用月份唯一约束进行幂等插入，冲突时保留已有任务全部状态。补建也执行同一入口。核算通过任务并发版本与事务一致性读取确定当前发布版本和确认数据，完成前再次检查输入版本；变化则拒绝提交并提示重试。归档在事务中检查结果版本、已应用状态及输入一致性，禁止边核算边归档。

计算结果与原始依据保存不可变版本；`payroll_review_edits` 保存任务、表、行键、明细字段覆盖、应用版本、修改理由、操作者、时间及版本。`payroll_custom_columns` 保存任务、目标表、字段ID、名称、类型及顺序；`payroll_custom_cells` 保存任务/表/行键/字段ID的类型受控值，组合唯一。归档事务冻结最终结果、追加表头和数据，写入归档月份。所有结果修改检查权限、状态及并发版本。

DEMO 仍采用浏览器本地存储：`monthlyPayrollJobs` 保存独立任务，`payrollScheduleStartMonth` 保存首次启用对应工资月，`publishedCompensationRules` 保存当前可用发布快照；`compensationTasks` 在 HR 核算时记录输入证据，Batch 保存计算结果、复核覆盖层及归档信息。登录后立即检查、窗口重新聚焦/恢复可见时检查，并每分钟检查一次。关闭网页期间不会执行后台工作，下次打开补齐已到期缺失任务；正式系统由上述后台调度器保障月初自动生成。沿用存储命名空间和版本，不清空历史。

## 验收示例

1. 北京时间2026-10-31 23:59仍不生成10月任务；11月1日00:00生成一条10月待核算任务；重复检查不增加任务。
2. 10月规则发布或修改不创建任务；11月1日即使数据为空也生成10月任务。发布无数据依赖，缺规则/数据的任务保持待核算。
3. 任务生成后发布v2并更新确认数据，HR核算使用v2与新数据，不使用创建任务时的版本。
4. 核算后仅保存v3草稿可继续复核；发布v3后必须重新核算才能归档。归档后再发布v4不改变历史结果。
5. 系统跨月关闭后重新打开补建缺失月份，已有任务、结果、已归档月份均不重复或覆盖。
